Technical Design

One language, end to end.
TypeScript everywhere.

The browser plugin must be JS/TS, and your data model is shared across plugin, API, worker, and dashboard. Picking TypeScript across the board means one type definition of a "submission" flows through the whole system - the single biggest maintainability win available here. Everything below follows from that.

02 Layer-by-layer rationale

🧩 Browser plugin — WXT

Modern Manifest V3 framework: TypeScript, HMR, and one codebase that builds for Chrome + Firefox. Content script scrapes the LeetCode/NeetCode submission (it uses a GraphQL API we can read); popup is React for the "Pull & Send" and manual capture UI. Plugin holds only a ShekseCodeSync token and POSTs to our API.

⚙️ API + worker — NestJS

Two processes from one codebase: the API handles capture/dashboard/auth; the worker drains the BullMQ queue for AI enrichment. NestJS's modules + DI keep a multi-domain, multi-user backend organized as it grows. Fastify is the lighter alternative if you'd rather stay minimal - but structure pays off here.

🗄️ Postgres + Prisma

Postgres handles concurrent writes (API + worker both write), JSONB for flexible metadata, and native full-text search for the dashboard. Prisma gives type-safe queries and first-class migrations. SQLite is tempting for a homelab, but multi-user + a worker pool make Postgres the durable call.

🔁 BullMQ + Redis

The async-AI decision needs a real queue. BullMQ is TS-native with retries, backoff, rate-limiting, and a ready-made dashboard (bull-board) - exactly what "fire-and-forget, retry on failure" wants. Redis is a tiny extra container and doubles as a cache/session store. pg-boss (queue-on-Postgres, no Redis) is the fewer-containers alternative.

🤖 AI layer — provider-agnostic

Your call: no vendor lock-in. The worker talks to a Vercel AI SDK (ai) unified interface behind our own tiny AiProvider in packages/ai. Swapping model = changing one env var, not code. generateObject + a Zod schema gives structured complexity/pattern/optimization output across providers. Default claude-opus-4-8; drop-in adapters for OpenAI, Google, or a local Ollama model on your homelab.

⚖️ Honest trade-off: a pure OpenAI-compatible wire format (code against the OpenAI SDK + a LiteLLM proxy) is maximally portable but lowest-common-denominator - you lose provider-native features (Claude's structured outputs, thinking). The AI SDK keeps portability and native strengths, so it's the better "no lock-in" answer. See the callout below.

📊 Frontend — Next.js

App Router + React for the dashboard, Tailwind + shadcn/ui for a clean owned component set, TanStack Query for data fetching, Recharts for insights (streaks, topic coverage, heatmap). CodeMirror 6 powers both the markdown question editor and the code editor in the manual-entry form.

🔐 Auth — Auth.js + GitHub App

Auth.js (NextAuth v5) handles multi-user login via GitHub OAuth. Separately, each user installs the GitHub App (Octokit) on their repo during onboarding - the backend mints short-lived per-commit tokens, exactly as designed in PRD §08. Plugin tokens are issued from the dashboard.

🐳 Packaging — Docker Compose

One docker-compose.yml brings up five services - web, api, worker, postgres, redis - on your homelab. The extension builds to a zip you load/publish separately. Config (GitHub App key, AI provider + key) via .env.

03 Monorepo shape

shekse-code-sync/
  apps/
    extension/   # WXT + React (MV3)
    api/         # NestJS HTTP API
    worker/      # NestJS AI-enrichment worker
    web/         # Next.js dashboard
  packages/
    types/       # @scs/types - shared DTOs
    db/          # Prisma schema + client
    ai/          # AiProvider interface + adapters
    github/      # Octokit / GitHub App helpers
  docker-compose.yml

Why this shape

  • • packages/types is the single source of truth for a "submission" - imported by extension, api, worker, and web. Change it once, everything type-checks.
  • • packages/db keeps Prisma schema shared between api and worker (both write).
  • • packages/ai isolates the provider swap (Claude ↔ Ollama) behind one interface.
  • • Turborepo caches builds so CI and local installs stay fast.

3b No AI vendor lock-in

Your question, answered: the model is a config value, not a dependency baked into the code. One interface, many providers.

// packages/ai - one interface
interface AiProvider {
  analyze(sol): Promise<Analysis>
}
// swap by env - no code change
AI_PROVIDER=anthropic
AI_MODEL=claude-opus-4-8
#   → openai / gpt-...
#   → ollama / llama3  (homelab)

✅ Chosen: Vercel AI SDK abstraction

Unified generateObject() with a Zod schema returns typed analysis from any provider. Portable and keeps each provider's native strengths. Adding a provider = one adapter package.

Alt: pure OpenAI-compatible wire (LiteLLM)

Code against the OpenAI SDK, point baseURL at a LiteLLM proxy that fronts every provider (incl. Ollama). Maximally standard, but lowest-common-denominator - you forfeit provider-native features. Good if you want the wire protocol itself to be the contract.
