01 Vision & Problem

The problem today

  • • You solve hundreds of problems but they vanish into LeetCode's history — no personal, portable record.
  • • Solutions aren't version-controlled, so you can't diff, review, or show your growth.
  • • Metadata (patterns, topics, weaknesses) lives only in your head, so revision is ad-hoc.
  • • You re-solve problems blindly instead of targeting your actual weak spots.
  • • No single view of progress across platforms, topics, and difficulty.

What ShekseCodeSync gives you

  • • A zero-effort capture pipeline — solve, submit, it's saved.
  • • A GitHub repo that becomes your public, browsable DSA portfolio.
  • • An AI reviewer that grades complexity, names the pattern, and suggests optimizations.
  • • A revision engine that builds the right quiz for your weaknesses.
  • • A dashboard that answers "how am I actually doing?" at a glance.
🎯 North-star: Every problem you touch leaves a durable, enriched, revisitable trace — with effectively zero manual bookkeeping.

05 Feature deep-dives

🔌 Capture — the plugin
  • • Auto mode: browser extension detects an accepted submission on LeetCode/NeetCode and scrapes title, statement, code, language, difficulty, tags/topics, companies, link, and runtime/memory stats.
  • • Pull button: a popup window with a "Pull & Send" action for when you want to capture on demand (or re-capture).
  • • Manual fallback: a web form (see Manual entry) for problems solved elsewhere or offline.
  • • De-dupe: re-submitting the same problem updates the record and adds a new solution revision rather than creating duplicates.
⚠️ Feasibility note: LeetCode exposes much of this via its GraphQL API; companies are often premium-gated. We'll confirm what's reliably scrapable during tech design.
🤖 AI analysis
  • • Complexity review: grades your solution's actual time & space complexity with a short justification.
  • • Auto-metadata: infers/normalizes tags, topics, and difficulty (useful for manual entries and cross-checking platform data).
  • • Optimization scan: flags whether a better approach exists and sketches it (without spoiling — configurable).
  • • Pattern attribution: names the underlying pattern (two-pointers, sliding window, BFS/DFS, DP, monotonic stack, union-find…) — this becomes a first-class revision dimension.
💡 Fire-and-forget: the API returns 200 as soon as GitHub + DB writes succeed, then enqueues the AI job. A background worker enriches the record later and the dashboard fills in AI fields when ready — the capture path never waits on the model. Re-runnable on demand from the dashboard. Failed jobs retry; the row simply stays "pending enrichment" until they succeed.
🔁 Revision engine
  • • Question banks assembled from your history: by isMarkedForRevision, by loophole/weakness, topic-wise, level-wise, or a mixed set.
  • • Quiz mode: generate a timed set; hide the solution, reveal after attempt, self-rate.
  • • Weakness targeting: problems with high attemptCount, wrong-first-submit, or low self-rating surface more often.
  • • Suggested (v2): spaced-repetition (Anki-style) scheduling so revision timing is automatic, not manual.
📊 Dashboard & insights
  • • Browse/filter all solved problems by topic, tag, date, level, pattern, platform, revision flag.
  • • Progress header: problems solved today / this week / this month, current streak, difficulty split.
  • • Insight cards: strongest & weakest topics, pattern coverage, hardest-fought problems, consistency heatmap.
  • • Click any problem → question + solution (rendered from GitHub) + AI notes + revision controls.
✍️ Manual entry
  • • Form accepts title + all metadata fields.
  • • Markdown editor (with preview) for the question statement.
  • • Language selector + code editor for the solution.
  • • Same downstream pipeline: writes to GitHub + DB, triggers AI enrichment.

🧭 What these choices imply for the build

  • • Auth: user accounts; each user connects their own GitHub repo (see §08 below).
  • • Isolation: DB rows scoped by userId; one worker pool serves all users' AI jobs.
  • • Self-hostable AI: pluggable provider — hosted API key or a local model on the homelab.
  • • One compose file: web + API + worker + DB + queue, all containerized.
  • • Queue required: the async AI decision means a real job queue is part of the stack.
  • • SRS schema: revision attempts need their own table (ease, interval, due date).

08 Auth & the GitHub connection

Your question: "how does the plugin authenticate with GitHub — does it create an app and authorize from GitHub?" Here's the design.

🔑 Core principle: the browser plugin never holds GitHub credentials and never talks to GitHub directly. It only talks to our backend. The backend owns the GitHub connection via a GitHub App.

Why a GitHub App (not PAT / OAuth)?

ApproachVerdict
GitHub App chosenFine-grained, per-repo install, short-lived tokens, revocable, higher rate limits. Best security + UX.
OAuth AppUser token with broad repo scope — more access than needed, no per-repo scoping.
Personal Access TokenUser pastes a token manually — works, but manual, long-lived, easy to leak. Offer only as a fallback.

Two separate auth boundaries

  • ① Plugin ↔ our backend: the plugin holds a ShekseCodeSync token (issued when you sign in / paste from the dashboard). This is not a GitHub token.
  • ② Our backend ↔ GitHub: handled once during web onboarding by installing our GitHub App on the repo you choose. Backend stores the installation ID and mints short-lived installation tokens per commit.

So the GitHub "authorize" screen appears in the web dashboard during setup, not in the plugin, and not on every submission.

⚠️ Self-hosting note: because you run this on your homelab, whoever deploys registers one GitHub App (a 2-minute step) and drops its App ID + private key into config. All users of that instance then install it on their repos. Documented in setup.

09 Risks & open questions

⚠️ LeetCode scraping fragility: DOM/API changes can break capture; companies data is premium-gated. Need a resilient capture strategy + graceful degradation.
⚠️ GitHub write path: GitHub App resolves auth (§08), but still need rate-limit handling + batching; large histories mean many commits.
⚠️ AI accuracy & cost: complexity/pattern calls cost tokens and can be wrong — need review/override + caching.
⚠️ Two-tier consistency: GitHub and DB can drift; need a reconcile/sync strategy and idempotent writes.
